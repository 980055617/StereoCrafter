step800 is ALSO the matched-optimiser-budget rung against mstudent1's step800, fixed by the
experimental design. Both pre-specified criteria coincide, so one render set was needed.
PREREGISTRATION.txt records the selection, and the shell output appended to it proves no test-clip
render of mstudent2 existed when it was written.

THE PRE-REGISTERED SHARPNESS TIE-BREAK WAS INSPECTED AND NOT APPLIED, AND IT WOULD NOT HAVE CHANGED
THE ANSWER ANYWAY. The rule was "within 0.0010 of the best, prefer the rung whose sharpness-vs-GT is
closer to 1.0". Its PRECONDITION is a meaningful sharpness difference between the contenders, and that
precondition is absent: the top three rungs sit at 1.310 / 1.314 / 1.316, a 0.5 % spread, so there is
nothing for the safeguard to object to. Its PURPOSE was to avoid shipping an over-sharpened
checkpoint, and the selected step800 is already the third-LEAST sharp of the six rungs. (Sharpness is
not even monotone in step here -- step1600 is 1.341 and step2000 is 1.340 -- so "later rung = sharper"
is not a rule that holds on this ladder.) Applied literally on the dev ladder's 0.0008 LPIPS span, a
0.0010 window swallows five of six rungs and the rule would have returned step200, a 1.5-epoch
checkpoint, on that 0.5 % sharpness difference. Both outcomes are on the record: the rule as literally
written selects step200 (dev 0.5472); the primary criterion selects step800 (0.5464). step800 is
independently the matched-optimiser-budget rung fixed by the experimental design, so it wins on BOTH
pre-specified grounds whatever the tie-break does -- the tie-break is not load-bearing for this
choice.

THE DEV SPLIT IS A WEAK INSTRUMENT, and this is a methodological finding in its own right. Its mean
GT sharpness is 0.0093 against the test set's 0.0164, i.e. it is skewed to the low-sharpness regime
where extra sharpening hurts; the shipped Mamba is already at 1.160x GT there; mstudent1 LOSES on
0245; and the whole mstudent2 ladder spans 0.0008 LPIPS. Dev and test also rank adjacent rungs
differently -- on the 4-clip test set mstudent1 ranks 600 > 800 (0.3822 vs 0.3838) while on dev it
ranks 800 > 600 (0.5454 vs 0.5457). Dev selection is cleaner than selecting on test, but it is also
blinder, and 0.0008 of spread cannot resolve a ladder.


4. DID MORE TRAINING CLIPS HELP?  NO -- IT HURT.  (the main result of this run)
------------------------------------------------------------------------------------------------
Three independent readouts agree, and the effect runs the wrong way on all three.

  (a) DEV, ladder vs ladder, clips neither run trained on, MATCHED optimiser budget (both step800):
          2 clips / 26 windows   0.5454        10 clips / 134 windows   0.5464      = +0.0010
      best rung vs best rung: mstudent1 0.5454 vs mstudent2 0.5464                  = +0.0010

  (b) THE TEN TEST CLIPS HELD OUT FOR BOTH RUNS (test minus mstudent1's 0301+0204):
          mamba 0.4084 -> mstudent1 s600 0.3949 (-0.0135)
          mamba 0.4084 -> mstudent2 s800 0.3982 (-0.0102)                           = +0.0033

  (c) THE EIGHT CLIPS CLEAN OF BOTH TRAINING AND SELECTION FOR EVERY ROW
      (test minus mstudent1's training clips 0301+0204 AND its selection clips 0052+0147;
       mstudent2 trained on none of the 12 and selected on dev):
          origin 0.3881 -> mstudent1 s600 0.3738 (-0.0144)
          origin 0.3881 -> mstudent2 s800 0.3773 (-0.0109)                          = +0.0035
      So mstudent1's advantage is NOT an artefact of having selected its rung on test clips: it
      survives on the set that is clean for both.

It is not undertraining either. The ladder has a visible optimum at step800 and degrades after it,
reaching WORSE-than-shipped-Mamba by step2000, so 5.2x the training data does not catch up at any
rung this run measured. At matched optimiser steps, more clips means fewer passes per window
(6 epochs over 134 windows vs mstudent1's 31 over 26) and that is the knob that changed; see
section 7 for the one experiment that would separate "more data is worse" from "more data needs a
different learning rate".

The origin-side run's own evidence pointed this way and was simply never tested: it reached 85.3 % of
the s25 gain on ten held-out clips from TWO training clips. The marginal value of more clips is not
merely modest here, it is negative.

8. THE SINGLE CHEAPEST REMAINING EXPERIMENT
------------------------------------------------------------------------------------------------
The negative scaling result has one untested confound: at matched optimiser steps, 10 clips means
6 passes per window where 2 clips means 31. The learning rate was held at 1e-5 for like-for-like, so
"more data is worse" and "more data needs a bigger step" are not separated. The cheapest test reuses
the capture already on disk (2657 s of target precompute, the expensive half) and only re-runs the
optimiser: ~2 GPU-h for two more 800-step arms at lr 3e-5 and 1e-4 from the same 402 cached targets,
scored on the 4-clip test set where the ladder has ~9x the dynamic range dev has (mstudent1 spans
0.3822-0.3896 there against dev's 0.0008). If neither arm reaches mstudent1's -0.0135 on the ten
held-out clips, "two clips is enough" is established and the 333-clip / 35-GPU-h plan should be
dropped outright rather than subsampled.
A second, independent gap worth one line: the selection instrument, not the model, is this run's
weakest component. Any future ladder should be selected on a set with the test set's sharpness
distribution, because dev's 0.0008 span cannot resolve adjacent rungs.
